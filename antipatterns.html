Resiliency anti-patterns: how to find them and fix them

Each anti-pattern below is one the animations demonstrate. Each entry says why it hurts, gives a command that finds it on a real cluster, explains the fix, and links to the animation that shows it happening. The commands need oc and jq and are read-only.

Placement and replicas

Where replicas run decides how much one node or zone failure costs.

One replica, or several replicas with nothing keeping them apart

Outage risk
Why

A single replica is down for every drain, reboot and crash. Several replicas with no spread constraint can still be bin-packed onto one node, so losing that node takes them all.

Check
oc get deploy,statefulset -A -o json | jq -r '.items[] | select(.spec.replicas < 2) | "\(.kind) \(.metadata.namespace)/\(.metadata.name)"'
oc get deploy -A -o json | jq -r '.items[] | select(.spec.replicas >= 2) | select(.spec.template.spec.topologySpreadConstraints == null and .spec.template.spec.affinity.podAntiAffinity == null) | "\(.metadata.namespace)/\(.metadata.name)"'
Fix

Run at least two replicas for anything user-facing, and add a topologySpreadConstraints entry on kubernetes.io/hostname (and on topology.kubernetes.io/zone when you span zones).

See it
Multi-replica: where it stopsRolling upgrade: neither

Hard placement rules with nowhere left to go

Stalls upgrades
Why

requiredDuringScheduling anti-affinity or whenUnsatisfiable: DoNotSchedule leaves pods Pending rather than bending the rule. During a drain the displaced replica has nowhere legal to land, and the drain waits on it.

Check
oc get pods -A --field-selector=status.phase=Pending
oc get events -A --field-selector reason=FailedScheduling \ | grep -Ei 'affinity|topology spread'
Fix

Use preferredDuringScheduling or ScheduleAnyway unless spreading is truly mandatory. If it is mandatory, keep more eligible nodes (or zones) than replicas so there is always somewhere to go.

See it
When required has no roomDoNotSchedule blocks

Disruption budgets

A PodDisruptionBudget controls how fast voluntary evictions can take replicas away. Too strict and nothing can move; missing and everything can.

minAvailable equal to the replica count

Stalls upgrades
Why

The budget allows zero disruptions, so no eviction can ever succeed. A node drain waits on it indefinitely and the whole MachineConfigPool rollout stops on that node.

Check
oc get pdb -A -o json | jq -r '.items[] | select(.status.disruptionsAllowed == 0) | "\(.metadata.namespace)/\(.metadata.name) expected=\(.status.expectedPods)"'
Fix

Prefer maxUnavailable: 1, which keeps working as the workload scales. If you must use minAvailable, keep it below the replica count.

See it
minAvailable = replicas: deadlock

No PodDisruptionBudget at all

Outage risk
Why

Nothing limits how fast a drain evicts. With maxUnavailable: 2 on the pool, or two drains running at once, every replica can be evicted in the same window, even if they are well spread.

Check
# namespaces that run Deployments but have no PDB comm -23 \ <(oc get deploy -A --no-headers | awk '{print $1}' | sort -u) \ <(oc get pdb -A --no-headers | awk '{print $1}' | sort -u)
Fix

Add a PDB with maxUnavailable: 1 for every multi-replica workload that serves traffic, selecting the same labels as the Deployment.

See it
Rolling upgrade: spread only

A PDB guarding pods that never become Ready

Stalls upgrades
Why

A PDB counts only Ready pods. If the replacement never passes readiness (bad image, missing secret, failing dependency), the budget never frees up, and the next eviction waits forever.

Check
oc get pods -A -o json | jq -r '.items[] | select(.status.phase == "Running") | select(any(.status.conditions[]?; .type == "Ready" and .status == "False")) | "\(.metadata.namespace)/\(.metadata.name)"'
Fix

Fix the reason the pod is not Ready before the maintenance window, not during it. Check these pods as part of the pre-upgrade checklist.

See it
When it never recovers

Expecting a PDB to protect a Deployment rollout

Outage risk
Why

A rollout deletes its own pods; it never calls the eviction API, so a PDB does not constrain it. With the default 25% / 25% strategy, capacity and availability both dip during every deploy.

Check
oc get deploy -A -o json | jq -r '.items[] | select(.spec.strategy.type == "RollingUpdate") | "\(.metadata.namespace)/\(.metadata.name) surge=\(.spec.strategy.rollingUpdate.maxSurge) unavail=\(.spec.strategy.rollingUpdate.maxUnavailable)"'
Fix

For latency-sensitive services set maxUnavailable: 0 and maxSurge: 1 explicitly, so every old pod waits for a Ready replacement.

See it
The 25% default

Probes and shutdown

What a pod reports about itself decides when it gets traffic, when it is restarted, and whether requests are dropped when it stops.

A slow starter with a liveness probe and no startupProbe

Outage risk
Why

The liveness probe starts counting before the application has finished booting, kills it, and the restart begins the same race again. The result is a CrashLoopBackOff for a pod that is healthy, just slow.

Check
oc get events -A --field-selector reason=Unhealthy | grep -i liveness
oc get deploy -A -o json | jq -r '.items[] | select(any(.spec.template.spec.containers[]; .livenessProbe != null and .startupProbe == null)) | "\(.metadata.namespace)/\(.metadata.name)"'
Fix

Add a startupProbe whose failureThreshold × periodSeconds covers the worst-case boot. Liveness only begins once it succeeds. Review the slow starters in the second list; fast-starting services don't need one.

See it
A slow starter without startupProbestartupProbe buys it time

No preStop delay, so in-flight requests are dropped

Outage risk
Why

SIGTERM and endpoint removal happen at the same time. For a moment the router still sends requests to a process that is already shutting down, and those requests fail even though every drain step went by the book.

Check
oc get deploy -A -o json | jq -r '.items[] | select(all(.spec.template.spec.containers[]; .lifecycle.preStop == null)) | "\(.metadata.namespace)/\(.metadata.name) grace=\(.spec.template.spec.terminationGracePeriodSeconds // 30)s"'
Fix

Add a short preStop sleep (5–10s) so endpoints drain first, handle SIGTERM by finishing in-flight work, and keep terminationGracePeriodSeconds above the sleep plus your longest request.

Resources and autoscaling

Requests are what the scheduler, drains and every autoscaler reason about. Wrong numbers here undermine everything else on this page.

Pods with no requests (BestEffort)

Outage risk
Why

The scheduler treats them as free, so nodes get overcommitted. Under memory pressure they are the first to be evicted. After a drain they fit anywhere on paper and nowhere in practice.

Check
oc get pods -A -o json | jq -r '.items[] | select(.status.qosClass == "BestEffort") | "\(.metadata.namespace)/\(.metadata.name)"'
Fix

Set memory and CPU requests on every container. A namespace LimitRange with defaultRequest catches anything that slips through.

See it
QoS classesNode under pressure

Requests copied from a template, not measured

Hidden drift
Why

Requests set too low overcommit nodes and skew HPA percentages; requests set too high waste capacity and block scheduling. Either way, every capacity calculation built on them is wrong.

Check
oc adm top pods -A --sort-by=memory | head -20
# compare with what those pods request oc get pods -n <ns> -o custom-columns=NAME:.metadata.name,REQ_MEM:.spec.containers[*].resources.requests.memory,REQ_CPU:.spec.containers[*].resources.requests.cpu
Fix

Run a VerticalPodAutoscaler with updateMode: "Off" on the biggest workloads to get recommendations without restarts, then set requests from real usage.

See it
VPA: how much

HPA and VPA driven by the same metric on the same workload

Outage risk
Why

VPA raising a request lowers the utilization percentage HPA reads, so HPA scales in just as load arrives. The two controllers keep undoing each other, and the workload thrashes.

Check
# workloads targeted by both an HPA and a VPA comm -12 \ <(oc get hpa -A -o json | jq -r '.items[] | "\(.metadata.namespace)/\(.spec.scaleTargetRef.name)"' | sort) \ <(oc get vpa -A -o json | jq -r '.items[] | "\(.metadata.namespace)/\(.spec.targetRef.name)"' | sort)
Fix

Keep VPA at updateMode: "Off" or "Initial" on HPA-managed workloads, or scale HPA on a metric VPA does not manage (requests per second, queue depth).

See it
Both, on the same metric

HPA minReplicas at or below the PDB floor

Stalls upgrades
Why

At night the HPA scales down to minReplicas. If that is no more than the PDB allows, the budget has no headroom and drains block. Size the drain check at maxReplicas, because a peak can land inside the maintenance window.

Check
oc get hpa -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,MIN:.spec.minReplicas,MAX:.spec.maxReplicas oc get pdb -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,MIN-AVAIL:.spec.minAvailable,MAX-UNAVAIL:.spec.maxUnavailable
Fix

Keep minReplicas at least one above the PDB's minAvailable (or use maxUnavailable on the PDB), and check drain capacity at maxReplicas.

See it
Capacity simulator: HPA & PDB

No headroom for a node to drain

Stalls upgrades
Why

When the rest of the pool cannot absorb a drained node's requests, evicted pods go Pending and the upgrade stalls halfway. On bare metal there is nowhere to surge to.

Check
# requested share of allocatable memory, per node oc describe nodes | grep -A8 "Allocated resources" | grep -E "Name:|memory"
Fix

Keep utilization during a roll at or below about 85% of what survives maxUnavailable, using allocatable (not capacity) and subtracting DaemonSet requests. The arithmetic and simulator pages do this for you.

See it
Fitting on a drainThe arithmeticSimulator

Trusting the manifest while ClusterResourceOverride rewrites it

Hidden drift
Why

An admission webhook changes requests and limits before scheduling, so the running pod differs from what you applied, and its QoS class can drop from Guaranteed to Burstable without anyone editing a manifest.

Check
oc get clusterresourceoverride cluster -o yaml 2>/dev/null oc get ns -l clusterresourceoverrides.admission.autoscaling.openshift.io/enabled=true
oc get pod <pod> -n <ns> -o jsonpath='{.status.qosClass}{"\n"}{.spec.containers[*].resources}{"\n"}'
Fix

Know which namespaces opt in, check the running pod rather than the manifest when reasoning about QoS or capacity, and exclude namespaces that need Guaranteed QoS.

Scheduling priority

When the cluster is full, priority decides who gets the room.

Critical workloads at default priority

Outage risk
Why

With no PriorityClass, a critical pod displaced by a drain waits in the same Pending queue as batch jobs. Overusing high priority is also dangerous: preemption deletes pods directly and bypasses PodDisruptionBudgets.

Check
oc get priorityclass
# namespaces with the most pods running at default priority oc get pods -A -o json | jq -r '.items[] | select(.spec.priorityClassName == null) | .metadata.namespace' \ | sort | uniq -c | sort -rn | head
Fix

Define a small number of PriorityClasses and reserve high values for truly critical services. Give batch work preemptionPolicy: Never so it waits instead of evicting others.

See it
Pending, regardless of priorityPreemption bypasses the eviction API

Storage

Volumes are zonal and outlive pods. That is what makes them useful, and it's also where these two anti-patterns bite.

volumeBindingMode: Immediate on zonal storage

Outage risk
Why

The volume is created before the pod is scheduled, in whatever zone the provisioner picks. If that zone has no room for the pod, or the pod's spread rules want another zone, it stays Pending, stranded beside its own data.

Check
oc get storageclass -o custom-columns=NAME:.metadata.name,BINDING:.volumeBindingMode,RECLAIM:.reclaimPolicy
Fix

Use WaitForFirstConsumer so the volume is created in the zone where the pod lands. The field is immutable, so create a new StorageClass and make it the default.

See it
Immediate can strand a zone

reclaimPolicy: Delete on data you cannot lose

Data loss
Why

Deleting the claim (a removed namespace, a Helm uninstall, a mistyped command) deletes the volume and its data with it. There is no confirmation and no undo.

Check
oc get pv -o custom-columns=NAME:.metadata.name,NS:.spec.claimRef.namespace,CLAIM:.spec.claimRef.name,POLICY:.spec.persistentVolumeReclaimPolicy
Fix

Patch critical volumes to Retain and back them up regardless. Retain keeps the disk, but it is not a backup.

oc patch pv <pv> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
See it

Upgrades

Cluster-level settings and state that decide whether an upgrade starts, how fast it moves, and whether it finishes.

MachineConfigPool maxUnavailable set without the capacity math

Stalls upgrades
Why

Set it too high and the surviving nodes cannot hold the evicted pods. Set it to 1 on a large pool and the upgrade outlasts the maintenance window.

Check
oc get mcp -o custom-columns=NAME:.metadata.name,MAX-UNAVAIL:.spec.maxUnavailable,MACHINES:.status.machineCount,PAUSED:.spec.paused
Fix

Derive it from drain headroom (see the simulator), and split very large or special-purpose groups into custom pools that can be paused and rolled separately.

See it
maxUnavailable: 2Custom pools

Starting an upgrade with a degraded ClusterOperator

Stalls upgrades
Why

The Cluster Version Operator upgrades operators in dependency order. One Degraded operator stops the graph before a single worker drains, and it looks like a stuck upgrade when it was never healthy.

Check
oc get clusteroperators -o json | jq -r '.items[] | select(any(.status.conditions[]; (.type == "Degraded" and .status == "True") or (.type == "Available" and .status == "False"))) | .metadata.name' oc adm upgrade
Fix

Clear every Degraded or unavailable operator before you start, and make oc get co the first command in the runbook, before any node-level checks.

See it
A degraded operator blocks everything

ROSA HCP machine pools left versions behind

Stalls upgrades
Why

Machine pools upgrade independently of the hosted control plane. Leave one far enough behind and the control plane itself refuses its next upgrade until that pool catches up.

Check
rosa describe cluster -c <cluster> | grep -i version rosa list machinepools -c <cluster> # compare each pool's version
Fix

Upgrade machine pools soon after each control-plane upgrade, with a canary pool first if the fleet is large, so no pool drifts toward the skew limit.

See it

Node autoscaling

Node autoscalers add and remove capacity, and removing a node is a disruption like any other.

Pods that pin nodes against scale-down

Wasted cost
Why

A pod annotated safe-to-evict: "false", a bare pod with no controller, or a PDB with no headroom keeps a nearly empty node running, and paid for, indefinitely.

Check
oc get pods -A -o json | jq -r '.items[] | select(.metadata.annotations["cluster-autoscaler.kubernetes.io/safe-to-evict"] == "false" or .metadata.ownerReferences == null) | "\(.spec.nodeName) \(.metadata.namespace)/\(.metadata.name)"' | sort
Fix

Remove the annotation wherever a restart is actually tolerable, run everything under a controller, and give every PDB at least one allowed disruption.

See it
Cluster autoscaler: scale down

Karpenter consolidation with no budgets

Outage risk
Why

Consolidation moves pods all day to save money. Without disruption budgets or do-not-disrupt on sensitive pods, those restarts land in business hours on workloads that cannot tolerate them.

Check
oc get nodepools.karpenter.sh -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.disruption}{"\n"}{end}'
Fix

Add disruption.budgets, including a scheduled nodes: "0" for business hours, and annotate pods that must not move with karpenter.sh/do-not-disrupt: "true". PDBs still apply on top of both.

See it
Karpenter: consolidation
